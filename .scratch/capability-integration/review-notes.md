# Capability integration review notes

Review policy: [docs/agents/review-policy.md](../../docs/agents/review-policy.md). Recorded findings are non-blocking:
no patch, no regression test, no new abstraction, no approval gate, and no blocking edge. Revisit only on a real
incident, new evidence of material impact, an explicitly triggered revisit condition, or explicit user prioritisation.

These are the known deferred findings that touch the surfaces this breakdown changes. They were recorded during the
earlier UX follow-up work (their full evidence is in [the UX follow-up review
notes](../ux-follow-up/review-notes.md)) and they are carried forward here so that a ticket that meets their revisit
condition does not rediscover them from scratch.

## Fixed by the final code review

Two findings from the review of the merged effort were material failures on ordinary paths, and each is fixed at the
layer that owned it. Both were found against the merged tip `191c477` and are fixed in the same change that records
them.

| # | Finding | Trigger and impact | Fix |
| --- | --- | --- | --- |
| 1 | The Web adapter sent this origin's own `HEPI_WEB_LOCAL_GATEWAY_ID` as `hostId` on a recorded Project's metadata operations (`PATCH /api/projects/:id`, `DELETE /api/projects/:id`, `DELETE /api/projects/:id/folders/:folderId`). The backend then compared that against the Project's recorded host and answered `409 wrong_host` (`apps/server/src/server.ts:991,1015,1048`). | A Project on a **configured remote gateway** — the ordinary SSH Project this effort delivered — could be created and listed from the Web origin, but never had its default changed, a folder unlinked, or itself removed: every one of those answered `wrong_host` with no way for the browser to name the right host. The adapter's own suite modelled `wrong_host` as an answer to forward, so the seam was covered for the refusal and not for the ordinary success. | The recorded Project's own host is the identity those routes act on. `apps/server/src/server.ts` resolves them through `projectHostOf()`, which takes the Project's `hostId`, accepts a named host only when it confirms that one, and still refuses a different one with `wrong_host` and an unconfigured one with `configuration_required`; `apps/web/adapters/durable-api.ts` stops naming a host on those three routes. Regression: `apps/web/adapters/remote-project-removal.test.mjs` — the Web adapter, a real backend with its own project store, and two real gateways, asserting a remote Project's create/list/default-change/unlink/removal all succeed from an origin whose own host is the other gateway, that the retained bindings are readable afterwards, that no directory changed, that the origin's own gateway received no registration, and that a caller naming another host is still refused. |
| 2 | `packages/gateway/src/terminal.ts` canonicalized the workspace root and the requested cwd with this machine's own `node:fs/promises` `realpath` **before** handing them to the launcher, for every workspace including SSH-owned ones. | A remote-only root — the normal case for an SSH Project, whose root is a directory of the SSH host — made the terminal fail outright: `realpath` reported `ENOENT` for a directory this machine does not have, so no shell could be opened in a remote Project's folder at all. Both entrypoints that compose the store were affected (`packages/gateway/src/main.ts`, `packages/client/src/gateway.ts`), and the existing SSH fixture could not show it because its root is also a path of the test machine. | Resolution and confinement stay the execution host's, as they already were for execution, files and workspaces. The gateway does only path arithmetic on the registered root and sends the requested directory; the Python helper on the execution host canonicalizes both, confines the cwd to the root, refuses a directory that does not exist there, and reports the root and cwd it accepted in its ready frame, which is what the session records and answers. The SSH transport no longer changes directory before starting the helper, so a directory the host does not have is the helper's own named refusal instead of a shell exit the gateway cannot classify. Regression: `packages/gateway/test/terminal.test.ts` — an isolated SSH fixture whose root exists only on that host (`sshd-fixture.ts` `isolated`), asserting the root is absent here, that a local `realpath` of it fails, that a session opens and reports the host's own root, and that a missing directory and one outside the root are both refused `path_denied` by the host. |

| 27 | The MCP surface reports a configuration file's parse failure to the browser with the raw parser message (`packages/gateway/src/mcp/config.ts:270` `problem: { reason: "unparsable", error: message(error) }`), which `apps/web/adapters/mcp-surface.ts` passes through as the file's `problems[].error`.
